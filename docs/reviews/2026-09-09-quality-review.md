## The picture in one paragraph


The architecture is sound and the process discipline is real (docs, ADRs, snapshot testing, review gates) — but
the **transfer engine loses data in ordinary situations**, and that is the product. Move with any non-overwrite
policy deletes the source after copying nothing; a same-connection Move ignores every conflict policy; cancelling an
overwriting *local* copy deletes the pre-existing file (the exact bug #190 fixed for SFTP — the local backend has
it too); F5 with both panes on the same directory truncates the file to zero; a FIFO in the tree hangs the app
with Esc dead; a symlink-to-dir aborts the copy half-way; Move out of an object store reports success and leaves
everything in the bucket. None of these has a test, and the engine's 19 tests are built on a mock that cannot
produce the conditions (no `AlreadyExists`, no `COPY_SERVER`, no `modified`, size always equals bytes written).
The second theme is **capabilities produced by every backend and consumed by nothing**: 14 of 19 `Caps` flags have
no non-test reader, the reducer never looks at `Caps`, and `actions_at` has no caller — so read-only backends
fail after the fact and directory copies into S3 die on `create_dir`. Third: **the two 8–13k-line files**
(`update.rs`, `app.rs`) hide a 16-argument `dispatch`, ten loose control tables and four identical `*Guard`
structs, with the runtime's lifecycle invariants untestable. Fourth, a cluster of **container-backend
correctness bugs** (symlinks read as empty, a non-zero `tar` exit discarding a complete listing, listing a
directory downloading its entire subtree) and a handful of **real security defects** (host-key
algorithm-swap accepted under `AcceptNew`, plugins setting their own sandbox limits, unbounded Argon2 params
from an unauthenticated header). The good news: almost every high is S or M effort, and they cluster into a
few PR-sized tracks (see the end).

## Confirmed high (15)

### Transfer engine: data loss and hangs

#### Copy/Move with both panes in the same directory destroys the file

**high** · ✅ confirmed · correctness · effort M · lens `bugs-core-reducer`  
`crates/cairn-core/src/update.rs`:2683

`start_transfer` builds `(from, to)` pairs by joining the source leaf name onto the *other* pane's cwd, with no check that the destination is the source. Cairn starts with both panes on two distinct `LocalVfs` connections rooted at the same fs_root and at the same launch directory (app.rs run_async), so F5/F6 on the very first keystroke produces `(x, x)`. Nothing downstream rejects it: the conflict prompt appears, and confirming it opens the file for read and then reopens the same path with `truncate(true)`, so the copy reads 0 bytes from the file it just emptied — and the size-verify passes because 0 == 0.

*Verifier:* Reproduced with the real engine. Probe: two `LocalVfs` on the same root with `ConnectionId(1)`/`(2)` (exactly `app.rs:213-216` LEFT/RIGHT startup shape), `run_transfer(&[(/notes.md, /notes.md)], ConflictPolicy::Overwrite, VerifyPolicy::Size)` on a 23-byte file → `result: Ok((1, 0))`, `file size after: 0`. Call path has no self-copy guard anywhere: `start_transfer` (update.rs:2683) joins the leaf onto the other pane's cwd unconditionally; `run_transfer_effect` (app.rs:2972-3008) only counts existing destinations and bounces `TransferConflict`; after the user confirms, `copy_file` (cairn-transfer lib.rs:~340) takes the stream path because conn ids differ, `open_read(from)` then `open_write(to, overwrite=true)` → `.truncate(true)` (backend-local lib.rs:212) empties the same inode, the read loop sees EOF, and the size-verify passes 0==0. `is_move` then `src.remove(from)` deletes what's left. No test covers this case (grep for self-copy/same-directory found nothing). User-reachable on the very first F5/F6 after launch with one Enter on the overwrite prompt; the prompt asks "overwrite?" which a user reasonably reads as "replace with a copy", so confirming is the natural action. Silent data loss → high stands.

**Fix:** Two layers. (1) Reducer, cheap and covers the startup case: in `start_transfer`, when `src_conn == dst_conn || both panes are LocalVfs over the same root` and `from == to`, drop the pair and set status "Cannot copy 'x' onto itself" (and don't return an empty transfer). Since conn ids differ at startup, either give both default local panes one shared `ConnectionId` (which also unlocks the same-conn rename/COPY_SERVER fast paths for local↔local) or add a `Vfs::identity()`/`local_path()`-style comparison. (2) Engine hard-fail, so no future caller can reintroduce it: in `copy_file` before `open_write`, if `src.connection() == dst.connection() && from == to`, or more robustly if `dst.stat(&to)` and `src.stat(from)` resolve to the same inode/identity for local backends, return a new `TransferError::SameFile(to)`. Also note `copy_within(from, from)` on the same-conn fast path has the same truncation hazard via `std::fs::copy`, so put the guard ahead of both branches. Add a regression test in cairn-transfer (two LocalVfs, same tempdir, same path, Overwrite) asserting the file is unchanged and the op errors.

#### Cancelling or failing an overwriting copy deletes the pre-existing destination file

**high** · ✅ confirmed · correctness · effort M · lens `bugs-vfs-transfer`  
`crates/cairn-backend-local/src/lib.rs`:351

`LocalVfs::open_write` writes straight to the final path with `truncate(true)` when overwriting, and `LocalWriteSink::abort` then does `remove_file(&self.full)`. The engine calls `writer.abort()` on cancel, on a read error and on a write error, so pressing Esc during a copy over an existing file leaves the user with neither the old file nor the new one. `ConflictPolicy::Overwrite` is what the app always passes (crates/cairn/src/app.rs:3015), so this is the default path.

*Verifier:* Traced: `LocalVfs::open_write` (crates/cairn-backend-local/src/lib.rs:206-222) opens the *final* path with `.truncate(opts.overwrite)`, so the existing file's contents are gone the instant an overwrite copy starts. `LocalWriteSink::abort` (lib.rs:351-354) then `remove_file(&self.full)` — the final path. The engine calls `writer.abort()` on cancel/pause-cancel, read error, write error, and post-loop cancel (crates/cairn-transfer/src/lib.rs:364, 376, 384, 400). `resolve_conflict` sets `overwrite: true` whenever the destination exists under `ConflictPolicy::Overwrite`, which is what `app.rs:3015/4478/4751` pass. Net effect: Esc mid-copy over an existing local file leaves neither old nor new file. Even without abort, the truncate-at-open means a crash mid-copy loses the original too.

Strong corroboration: the SSH backend had the identical bug and fixed it with temp+rename; its test `cancelled_overwrite_preserves_the_existing_file` (crates/cairn-backend-ssh/src/lib.rs:736-765) is commented "opening the *target* with CREATE|TRUNCATE destroyed the user's existing file the instant an overwrite copy started, so cancelling it (which aborts the sink) left them with nothing." The local backend never received that fix. No local test covers abort at all.

Severity high is correct: silent destruction of user data on the default, most common path (local→local copy, Esc). Fix note beyond the proposal: also handle the non-overwrite case correctly — with a temp+rename, `create_new` on the target is lost, so mirror the SSH backend's check (fail with `AlreadyExists` if the target appeared between open and finish, then remove the temp). Trade-off to state in the PR: rename replaces the inode, so the original's mode/owner/hardlinks are not preserved (same as SSH today); acceptable, but document it.

**Fix:** In `LocalVfs::open_write`, when `opts.overwrite` (or always, for symmetry with SSH): create a sibling temp (`<name>.<rand>.part` via `OpenOptions::create_new`, not `tempfile::NamedTempFile` which forces 0600 perms) in the same directory; write/fsync to it; in `finish` `tokio::fs::rename(temp, full)` (atomic replace on POSIX, replaces on Windows too). If `!overwrite`, before rename check `symlink_metadata(full)` and return `AlreadyExists` (remove temp) so create_new semantics survive. `abort` removes only the temp; on any `finish` failure remove the temp too. Regression tests in cairn-backend-local: (1) pre-seed `/keep.txt`, open_write overwrite=true, write a chunk, `abort()`, assert content == original and no `.part` left; (2) same but `finish()` replaces content; (3) abort on a fresh file leaves nothing behind. Optionally, in the transfer engine or a shared test, add a cancel-mid-copy-over-existing-file test to lock the end-to-end behavior for all backends.

#### A FIFO or device node in the source tree hangs the transfer forever and ignores cancellation

**high** · ✅ confirmed · concurrency · effort M · lens `bugs-vfs-transfer`  
`crates/cairn-transfer/src/lib.rs`:302

`copy_tree` routes everything that is not `EntryKind::Dir` to `copy_file`, including `EntryKind::Special`. `LocalVfs::open_read` then calls `tokio::fs::File::open` on the FIFO, which blocks in the blocking pool until a writer appears. The engine's cancellation checks all sit inside the chunk loop, which is never reached, so Esc does nothing and the wedged blocking task also stalls tokio runtime shutdown (my first probe run never exited).

*Verifier:* Reproduced independently with a scratch binary linking cairn-transfer + cairn-backend-local (workspace HEAD): a tree {a.txt, mkfifo pipe} copied via run_transfer with cancel fired at 2s printed "RESULT: HUNG 5s despite cancel at 2s", and the process then never printed "runtime dropped" — killed by the 20s outer timeout, i.e. Runtime::drop wedges on the blocking-pool open(). Code path: copy_tree (lib.rs:290-302) only tests `meta.is_dir()` and sends everything else to copy_file; LocalVfs::stat uses symlink_metadata and entry_from_meta does classify FIFOs as EntryKind::Special (local/lib.rs:117), but the kind is discarded. copy_file then calls LocalVfs::open_read -> tokio::fs::File::open (local/lib.rs:188), which is spawn_blocking and blocks in open(2) until a FIFO writer appears; no cancel check precedes or wraps that await, so Esc cannot interrupt it. cairn-core already refuses F3/F4 on Special for exactly this reason (update.rs:3393, 9626), so the transfer engine is the one caller that forgot. Reachable by any F5/F6 of a directory containing a named pipe (common in ~/.cache, dev trees, container roots). Severity high stands: unbounded hang, cancel ignored, and runtime shutdown blocked.

**Fix:** Two layers, both cheap: (1) In copy_tree match on `meta.kind`: `Dir` -> existing branch; `Special` (and `Stream`) -> `outcome.skipped += 1` plus a Warning/Skipped progress event naming the path, never opened; `File`/`Symlink` -> copy_file. (2) Defense in depth in LocalVfs::open_read: `tokio::fs::metadata(&full)` (follows symlinks) before `File::open`, and return a typed error (e.g. VfsError::Unsupported/NotAFile) when `!is_file()` — this also covers a symlink pointing at a FIFO, which layer (1) misses because stat is symlink_metadata and would report `Symlink`. Drop the O_NONBLOCK idea: it is Unix-only, needs unsafe/extension traits, and a non-blocking FIFO read still never yields EOF. Regression tests: a `#[cfg(unix)]` cairn-backend-local test that mkfifo's a node and asserts open_read errors promptly, and a cairn-transfer test (MockVfs entry with EntryKind::Special) asserting the tree copy completes with skipped == 1 and the mock's open_read never called.

#### A symlink-to-directory inside a copied tree aborts the whole transfer and leaves a half-written destination

**high** · ✅ confirmed · correctness · effort M · lens `bugs-vfs-transfer`  
`crates/cairn-transfer/src/lib.rs`:290

`copy_tree` decides dir-vs-file with `meta.is_dir()`, and `LocalVfs::stat` uses `symlink_metadata`, so a symlink is never `Dir`. A symlink pointing at a directory therefore goes to `copy_file`, where `File::open` succeeds on the directory fd and the first `read()` fails with EISDIR — killing the entire transfer partway through. Plain file symlinks are silently dereferenced into full copies, which for a Move also means the link is replaced by data and then the original deleted.

*Verifier:* Reproduced with a scratch binary linked against the real crates (LocalVfs + cairn_transfer::run_transfer, local->local copy of `/src` containing `plain.txt`, `real/inner.txt`, `link -> real`, `flink -> plain.txt`):

- With the dir symlink: `result: Err("io error")`, `dst contains: ["plain.txt", "real"]` — transfer aborts, destination half-written, `link` never created. Path: `copy_tree` (crates/cairn-transfer/src/lib.rs:290) tests `meta.is_dir()`, which is `matches!(kind, EntryKind::Dir)` (cairn-types/src/entry.rs:49); `LocalVfs::stat` uses `symlink_metadata` (cairn-backend-local/src/lib.rs:175) and `entry_from_meta` yields `EntryKind::Symlink`, so it falls to `copy_file`; `File::open` on a directory succeeds on Linux, first `read()` -> EISDIR -> `VfsError::Io`.
- Without the dir symlink: `Ok(files: 3, dirs: 2)`, `flink: symlink=false` — a file symlink is silently dereferenced into a regular-file copy (files count includes it).

One overstatement in the claim: for a same-connection Move, `transfer_one` takes the `rename` fast path (Caps::RENAME) and never walks the tree, so "link replaced by data then original deleted" only applies to cross-connection moves. `crates/cairn-transfer` has no symlink test at all (grep for "symlink" in the crate is empty). SSH backend also reports `EntryKind::Symlink` via LSTAT (cairn-backend-ssh/src/real.rs:131), so the same abort applies to SFTP sources.

**Fix:** In `copy_tree`, match on `meta.kind` instead of `is_dir()` and add an explicit `EntryKind::Symlink` arm. Minimal safe version: if `dst.caps_at(&t)` has a symlink capability (add `Caps::SYMLINK` + `Vfs::symlink(target, path)` with a default `Unsupported` impl; `Entry.symlink_target` already exists — populate it in `LocalVfs::stat` via `read_link`), recreate the link; otherwise `outcome.skipped += 1` and record the path/reason so the summary can list it, never fall through to `copy_file`. Also treat `EntryKind::Special` the same way (sockets/FIFOs would hang or fail on `read`). Add a regression test in `crates/cairn-transfer` (it has none for symlinks) using a tempdir + `LocalVfs` with `link -> real/` asserting the transfer completes and the rest of the tree lands. A dereference option can follow as a separate `TransferSpec` field.

#### Move from an object store reports success but leaves the source prefix in place

**high** · ✅ confirmed · correctness · effort M · lens `qa-engine-backends` · also seen by bugs-remote-backends  
`crates/cairn-backend-object/src/vfs.rs`:165

ObjectStoreVfs::remove ignores Recurse and issues a single delete of the key; for a 'directory' (a prefix with no marker object) that is a no-op, and every provider's delete of a missing key is Ok. The engine's Move therefore copies the tree, calls remove(Recurse::Yes), gets Ok, and the UI shows 'Moved N files' while every object is still in the bucket. F6 from an S3 pane is reachable today. The same idempotent-Ok means the F8 delete walk counts a stale entry as 'Deleted'.

*Verifier:* Reproduced independently with a scratch crate against the real code (crates/cairn-backend-object/src/vfs.rs:165-168 + crates/cairn-transfer/src/lib.rs:260-264): Move of prefix `/d` from ObjectStoreVfs(MockObjectStore{d/a}) to MockVfs returns `Ok(TransferOutcome{files:1,dirs:1,bytes:3})`, yet afterwards `src.stat(/d/a) = Ok(Some(3))` and `src.stat(/d) = Ok(dir)`; `remove(/zzz, No) = Ok(())` and `remove(/d, No)` on a non-empty prefix = `Ok(())`. Mechanism: `remove` ignores `Recurse`, deletes key `d` (never `d/...`, never the `d/` marker), and every provider's delete of a missing key is Ok (S3 204; azure.rs:215 explicitly maps 404->Ok; mock is a plain HashMap remove). The engine's `transfer_one` then treats the Ok as a completed move and app.rs reports "Moved". Reachable: S3/GCS/Azure connect in crates/cairn/src/connect/mod.rs behind the `s3`/`gcs`/`azure` features and the stores declare `Caps::DELETE`, so F6 is not gated off. Scope corrections to the report: (a) only *directory* moves are affected — a single-object move deletes its key correctly; (b) the F8 walk is not broken in the same way — it removes leaf objects individually with Recurse::No and does delete them; its defects are cosmetic (a no-op prefix delete counts as "Deleted", a stale entry counts as "Deleted") plus one real leftover: a zero-byte `dir/` marker object is never deleted (key is `dir`, not `dir/`), so an explicitly-created folder survives F8. Severity stays high: silent false success on a core operation; it is data duplication rather than data loss, but the user is told the source is gone when it isn't, and the `Recurse` contract in cairn-vfs/src/vfs.rs:110-117 is simply not honored.

**Fix:** Implement `remove` in ObjectStoreVfs by resolving the path first rather than trusting provider delete semantics: (1) `head(key)` Ok -> `delete(key)` (plain object). (2) Else `list_page(key+"/", None /*flat, no delimiter*/, token, 1000)` paginated: if empty -> `Err(NotFound)` (this also fixes idempotent-Ok on missing keys at the Vfs layer without touching the provider `delete` contract, which azure.rs deliberately keeps idempotent for retry safety). (3) If non-empty and `Recurse::No`: allow only when the sole object is the marker `key+"/"` (delete it), otherwise return an error (`VfsError::Backend{code:"DirectoryNotEmpty", ..}` or a new variant — there is no NotEmpty variant today; check what cairn-backend-local returns for rmdir on a non-empty dir and match it). (4) If `Recurse::Yes`: delete every listed key including the `key/` marker, then the bare key; batch via S3 DeleteObjects (up to 1000 keys) as a follow-up optimisation, per-key delete is correct first. Tests: in vfs.rs add `remove(/logs, Yes)` then `stat(/logs)`/`stat(/logs/2026/b.log)` -> NotFound; `remove(/logs, No)` -> Err; `remove(/nope, No)` -> NotFound; marker-object dir removed by `remove(No)`. In cairn-transfer add a Move test with ObjectStoreVfs as source asserting the source tree is gone after Ok. Add the same assertions to the live S3/Azure/GCS `CAIRN_IT_*` suites. Also retire the stale "(M5)" comment on line 166.

#### Copying a directory into any object-store backend fails with Unsupported(CREATE_DIR)

**high** · ✅ confirmed · correctness · effort S · lens `qa-engine-backends` · also seen by bugs-remote-backends  
`crates/cairn-transfer/src/lib.rs`:291

copy_tree unconditionally calls dst.create_dir for every directory and only tolerates AlreadyExists. ObjectStoreVfs never overrides create_dir (object stores have no directories), so the trait default returns Unsupported(CREATE_DIR) and the whole transfer aborts before a single byte moves. F5 on a local folder with an S3/GCS/Azure pane as destination cannot work; nothing in cairn/app.rs gates on CREATE_DIR, and the live MinIO/Azurite suites only PUT single objects so CI never sees it.

*Verifier:* Static trace confirms it without needing the probe. `Vfs::create_dir` default (crates/cairn-vfs/src/vfs.rs:158) returns `Err(Unsupported(Caps::CREATE_DIR))`. `ObjectStoreVfs` (crates/cairn-backend-object/src/vfs.rs:71-175) implements list/stat/open_read/open_write/remove/copy_within only — no `create_dir` override, and its caps (s3.rs:42, gcs.rs:60, azure.rs:48, mock.rs:54) omit CREATE_DIR. `copy_tree` (crates/cairn-transfer/src/lib.rs:291-295) matches `Ok`, `AlreadyExists`, and `Err(e) => return Err(e.into())`, so the very first directory node aborts the transfer before any `copy_file`. `cairn/src/connect/mod.rs:197-198` wraps `s3_connect`'s `ObjectStoreVfs` directly in `Arc<dyn Vfs>` with no adapter, and `grep CREATE_DIR` in crates/cairn/src and crates/cairn-core/src is empty, so nothing upstream gates the op. Same path is hit for Move→object-store (no RENAME cap either, so it falls into copy_tree). Docker/K8s lack WRITE entirely so they are not additionally affected. All existing cairn-transfer tests use `MockVfs`, whose caps include CREATE_DIR (cairn-vfs/src/mock.rs:172), which is why this is invisible in CI.

**Fix:** In copy_tree, gate on capability rather than swallowing the error: `if dst.caps_at(&t).contains(Caps::CREATE_DIR) { match dst.create_dir(&t).await { Ok(()) => outcome.dirs += 1, Err(VfsError::AlreadyExists(_)) => {}, Err(e) => return Err(e.into()) } }` — do not add a blanket `Err(Unsupported(_)) => {}` arm, since that would also mask a backend that advertises CREATE_DIR but fails it. Note the consequence: on object stores an empty source directory produces no object and is silently dropped; either document that in the transfer rustdoc or count it in `outcome.skipped`. Tests: add a `MockVfs` variant (or a caps-override constructor) without CREATE_DIR and assert a two-level tree copies with `dirs == 0` and all files present; and add a run_transfer directory-copy case to the MinIO/Azurite live suites and to cairn-backend-object's own tests against `MockObjectStore` (that one runs hermetically, so it should be the primary regression test).

### Container backends (Docker/K8s): wrong results

#### A non-zero tar exit throws away a complete listing: any container running as non-root is unbrowsable

**high** · ✅ confirmed · correctness · effort S · lens `bugs-container-backends`  
`crates/cairn-backend-k8s/src/real.rs`:627

`list_dir` only parses `out.stdout` when `out.is_success()`. GNU tar exits 2 whenever *any* descendant is unreadable, while still writing a complete, valid archive of everything it could read. So listing a directory inside a container that runs as a non-root user (the hardening default for most images) discards a perfectly good listing and returns a raw `exec-failed` backend error instead. The same gate turns a listing of `/` into a spurious `NotFound` on any container with a live `/proc`, because vanishing procfs entries make tar print "Cannot open: No such file or directory", which `is_path_not_found` matches.

*Verifier:* Reproduced with GNU tar 1.35: `mkdir -p d/sub; touch d/readable; chmod 000 d/sub; tar cf - -C d . > out.tar` exits 2 with stderr `tar: ./sub: Cannot open: Permission denied` / `Exiting with failure status due to previous errors`, yet `tar tvf out.tar` lists `./` and `./readable`. In `crates/cairn-backend-k8s/src/real.rs:627` `list_dir` only calls `parse_list_dir(&out.stdout)` when `out.is_success()` (Status == "Success"); otherwise `into_vfs_err` runs: exit 2 is not 126/127 and stderr has no OCI phrase, so not exec_unavailable; "Permission denied" matches nothing in `is_path_not_found`; result is `VfsError::Backend{code:"exec-failed"}` and the valid stdout is dropped. Because the command recurses the whole subtree (`tar cf - -C <path> .`), any unreadable descendant anywhere below the listed dir (e.g. /etc/shadow when listing /etc, /root when listing / as non-root) trips this. One correction to the claim: the listing in stdout is not "complete" — tar omits the unreadable child (`./sub` is absent), so the salvaged listing is partial; still far better than an error. The kind integration test only lists `/` as root, so it does not cover this. Severity high is warranted: the k8s in-container browsing feature fails on the common non-root hardened container on a user-reachable path (loud error, not silent, but feature-blocking).

**Fix:** In `list_dir` (real.rs:627), attempt `parse_list_dir(&out.stdout)` first whenever stdout is non-empty and parses to at least one tar header (the root `./` entry counts), regardless of `is_success()`; fall back to `Err(out.into_vfs_err(path))` only when stdout is empty or unparseable. Optionally recover the omitted names from stderr lines matching `tar: ./<name>: Cannot open: Permission denied` (GNU) / `tar: can't open './<name>'` (BusyBox) and append them as entries with unknown kind/size so the partial listing is not silently missing children. Add a unit test in real.rs's test module: `ExecOutput { stdout: <tar with ./ and ./readable>, stderr: b"tar: ./sub: Cannot open: Permission denied\n", status: Some(make_status(2)) }` asserting `Ok` with `readable` present. Separate follow-up worth tracking: `tar cf - -C <path> .` archives the entire subtree just to list immediate children (listing `/` streams the whole container fs); use `--no-recursion` with explicit children where the container's tar supports it.

#### Symlinked files read as empty: copying /bin/sh or /etc/resolv.conf out of a container silently yields a 0-byte file

**high** · ✅ confirmed · correctness · effort M · lens `bugs-container-backends`  
`crates/cairn-backend-docker/src/real.rs`:806

Both backends archive the requested path without dereferencing symlinks, so the single tar entry they get back is the symlink itself, whose header size is 0 and whose body is empty. `read` happily returns `Ok(vec![])`. The file manager then shows an empty file and, on copy, writes a 0-byte destination file with no error at all — silent data loss on paths that are symlinks in essentially every container image (`/bin/sh`, most of busybox's `/usr/bin`, `/etc/localtime`, `/etc/resolv.conf` on many bases).

*Verifier:* Both `read` paths take the first tar entry, reject only `is_dir()`, and `read_to_end` it (crates/cairn-backend-docker/src/real.rs:815-820, crates/cairn-backend-k8s/src/tar_exec.rs:175-190). A symlink entry has header size 0 and no body, so `read` returns `Ok(vec![])`.

k8s: probe `tar cf - -C p link` (link -> target containing "hello") produced an entry of type '2' (symlink), size 0; with `-h` the same command produced a 6-byte regular file. The k8s backend argv at real.rs:697 is `["tar","cf","-","-C",parent,basename]` — no `-h`, so any symlinked file (`/bin/sh` on busybox/alpine, `/etc/localtime`) reads as empty.

Docker: `GET /containers/{id}/archive` only resolves the *parent* directory (moby `Container.ResolvePath` splits dir/base and resolves dir only) and tars the lstat'd final component, which is why `docker cp -L` exists; the code at real.rs:739 already acknowledges the endpoint returns symlink entries. Could not probe the daemon here (socket permission denied), but the mechanism is the same as the k8s one. No test in either crate covers a symlink entry (grep: only the list_dir/stat branches mention symlinks). The copy path writes whatever `read` returns, so the user gets a 0-byte destination with no error — silent data loss, high is correct.

**Fix:** k8s: change the read (and stat) argv to `tar chf - -C <parent> <basename>` (`-h` is supported by both GNU and busybox tar; probe confirmed it yields a regular file entry with the target's bytes). Hard-link entries cannot occur in a single-member archive, so no handling needed there.

**high** · ✅ confirmed · performance · effort L · lens `bugs-container-backends`

#### AcceptNew host-key policy silently learns a *different-algorithm* host key for an already-known host

**high** · ✅ confirmed · security · effort M · lens `bugs-remote-backends`

### SSH / archive / object backends

#### Ordinary .tar.bz2 / .tar.zst archives are refused as "multi-stream" because the guard scans compressed entropy for a 3-byte magic

**high** · ✅ confirmed · correctness · effort M · lens `bugs-remote-backends`  
`crates/cairn-backend-archive/src/compressed_tar.rs`:421

After a successful bzip2/zstd decode, `decompress_to_temp` scans the whole compressed file for a second occurrence of the format magic and refuses the mount if it finds one. BZIP2_MAGIC is `"BZh"` — three bytes — so it recurs by chance roughly once per 2^24 bytes of high-entropy compressed output. Any moderately sized .tar.bz2 therefore has a large probability of being rejected with `compressed_tar_multi_stream`, i.e. the user simply cannot open their archive. ZSTD_MAGIC (4 bytes) has the same defect at ~256x lower rate, which still bites at the ~512 MiB cap.

*Verifier:* Reproduced end-to-end. `decompress_to_temp` (compressed_tar.rs:419-424) calls `contains_magic_after_start(path, compression.magic())` after a successful decode; for bzip2 the magic is the 3-byte `b"BZh"` (archive_magic.rs:24), and the scan matches any byte offset >= 1 in the raw compressed bytes. Probe: `tar -cf` of this repo's `crates docs` (4.0 MB) x20 + 64 KiB random → `bzip2` → 14.5 MB `.tar.bz2`; a byte scan finds `BZh` at offset 11714699 in all 5 variants. Opening it through the real crate (scratch binary calling `ArchiveVfs::open`) returns `Backend { code: "compressed_tar_multi_stream", msg: "multi-stream/multi-frame bzip2 archives are only partially decoded..." }` while the same tar as `.zst` and a 46-byte `.tar.bz2` open OK. Expected false-positive count is ~compressed_len / 2^24, so a ~16 MB .tar.bz2 is refused ~60% of the time and a 100 MB one essentially always — with an error that wrongly tells the user their archive is multi-stream. Zstd's 4-byte magic has the same defect at 1/256 the rate (0 hits in my 18 MB samples, but ~3% at 512 MB). The only covering test (`decompresses_and_indexes_a_real_bzip2_tar`) uses a 20-byte payload and cannot observe the collision. The doc comment on `contains_magic_after_start` calls the false positive "extremely rare" — that estimate is off by orders of magnitude for a 3-byte magic. Severity: not data loss, but a deterministic, user-reachable refusal of ordinary valid archives with a misleading error — the .tar.bz2 feature is effectively broken above ~10 MB, so high stands.

**Fix:** Bzip2: keep the byte scan but require a genuine stream header at the hit, not just `BZh`: `BZh` + ASCII `1`..`9` + the 6-byte block magic `31 41 59 26 53 59` or end-of-stream magic `17 72 45 38 50 90` (10 bytes; chance collision ~2^-72; real concatenated bzip2 streams are byte-aligned so this is exact for the case being guarded). Zstd: drop the scan; `ruzstd::StreamingDecoder` reads exactly one frame, so after `io::copy` check the inner reader for any remaining bytes (`decoder.inner()`/`into_inner()` then a 1-byte read) — a reliable consumed signal for this decoder, unlike bzip2-rs. Fix the "extremely rare" claim in the doc comment. Add a regression test that runs the guard over a buffer containing `BZh9` + non-magic bytes (and, cheaper than a 16 MB fixture, a synthetic `BZh` occurrence mid-buffer) asserting no refusal, plus keep the existing true-multistream positive case. Longer term (RFC-0013 follow-up) decode successive streams in a loop instead of refusing.

Add a reducer test `quit_with_active_transfer_opens_confirm` and one asserting `should_quit` only flips after the last `TransferDone`.

*Verifier:* Code confirms it: `transfer_one` (crates/cairn-transfer/src/lib.rs:251-257) returns after `src.rename(from, to)` on a same-connection Move with `Caps::RENAME`; `resolve_conflict` is only called from `copy_file` (lib.rs:326), which this path never reaches. `LocalVfs::rename` is a bare `tokio::fs::rename` (cairn-backend-local/src/lib.rs:247), which replaces an existing file, so Skip/Prompt/Rename/NewerWins are all silently ignored. The executor comment at crates/cairn/src/executor.rs:176-178 explicitly acknowledges the gap ("takes the engine's rename fast-path which ignores the policy and would overwrite"). No engine test covers move-onto-existing on one connection (tests at lib.rs:777/886/1060 use empty destinations), and `MockVfs::rename` (cairn-vfs/src/mock.rs:297) clobbers too.

Severity correction: both in-tree callers already work around it, so no shipped path loses user data today. The TUI (crates/cairn/src/app.rs:2975-3005) stats every destination up front, raises `TransferConflict` for the user, and only then runs with `ConflictPolicy::Overwrite` — where rename-replace is the intended result. The AI executor pre-stats and rejects. The defect is a broken public library contract (rustdoc on `ConflictPolicy` and RFC-0002 line 41 both promise stat-before-write) plus a TOCTOU window between the callers' pre-flight and the rename, not a live data-loss bug in the product. Medium, not high.

**Fix:** In `transfer_one`, before the fast path call `resolve_conflict(src, dst, from, to, spec.conflict)`: on `Skip` bump `outcome.skipped` and return; on `Err(Conflict)` propagate; on `Write { path, .. }` rename to `path` (the `Rename` policy's `name (1)` target). Keep one caveat: if the source is a directory and the destination exists as a directory, `rename(2)` fails (EEXIST/ENOTEMPTY) rather than merging — for that case fall through to `copy_tree` + `remove` so directory-merge semantics match the cross-connection path. #### In-container path is passed to tar as a bare operand: argument injection, and any file whose name starts with `-` is unreadable

**~~high~~ → medium** · ✅ confirmed · security · effort S · lens `bugs-container-backends`  
`crates/cairn-backend-k8s/src/real.rs`:663

`stat` and `read` build `["tar","cf","-","-C",parent,basename]` with no `--` separator, so a container-controlled file name that begins with `-` is parsed by tar as an *option*, not as the file to archive. A hostile or merely awkward image can therefore make Cairn feed arbitrary tar options into the exec it runs inside the container — e.g. `--files-from=list` redirects which files end up in the archive, so `read` returns some other file's bytes than the one the user opened. *Verifier:* Confirmed the mechanics. `crates/cairn-backend-k8s/src/real.rs:663` and `:697` build `["tar","cf","-","-C",parent,basename]` and pass the argv straight to `Api::exec` (real.rs:263); `tar_basename` (tar_exec.rs:37) does no sanitizing, and nothing in the path layer rejects a leading `-`. Probe with GNU tar 1.35: `tar cf - -C d -foo` exits 2 ("Multiple archive files require '-M' option"), `tar cf - -C d "--files-from=list"` exits 2 ("list: Cannot stat"), while `tar cf - -C d -- -foo` exits 0 and archives the file. `into_vfs_err` (real.rs:155) then maps the failure to NotFound or a generic "exec-failed" Backend error, so any file whose name starts with `-` lists fine but can never be stat'd or opened in the k8s backend.

Severity is overstated. The exec runs inside the container with the container's own privileges, so a hostile image feeding tar options gains nothing it does not already have (it could equally symlink `-foo` to `other`). The real, user-visible defect is a correctness one: dash-prefixed files are unreadable and, in a crafted image, `read` can return the wrong bytes without a shell or client-side compromise. That is medium, not high.

**Fix:** Add the `--` end-of-options separator before the operand in all three argv builders: `["tar","cf","-","-C",parent,"--",basename]` at real.rs:663 and :697, and `["tar","cf","-","-C",path,"--","."]` at :624 for consistency (both GNU and busybox tar honor `--`). Add a unit test in tar_exec.rs/real.rs asserting the argv shape for a basename such as `-foo` and `--files-from=x`, and note in the docs comment that `--` guards against option-like names. Consider the same check in the Docker backend if it shells out to tar with a bare basename.

#### VfsPath's traversal guard is '/'-only: backslash and drive-letter segments escape the backend root on Windows

**~~high~~ → medium** · ✅ confirmed · security · effort S · lens `bugs-vfs-transfer` · also seen by qa-engine-backends  
`crates/cairn-types/src/path.rs`:52

`VfsPath::parse` splits on `/` and rejects only `..` and control characters, so `..\..\Windows\win.ini` and `C:\Windows\win.ini` survive as a *single* segment. `LocalVfs::resolve` then does `pb.push(seg)`, and on Windows that either appends a `..`-bearing component the OS resolves away, or (for a drive-qualified segment) replaces the base path outright. Windows is a supported target (CI builds it; commit 161b0fe fixes Windows builds), and path.rs claims this guard is what keeps a path "from escaping its backend root (important across the plugin/AI trust boundary)".

*Verifier:* Code does what the finding says. `VfsPath::parse` (crates/cairn-types/src/path.rs:52-57) splits only on `/` and rejects only the literal segment `..` plus control chars; `join` (line 112) rejects `/` but not `\`. So `..\..\Windows\win.ini` and `C:\Windows\win.ini` each become one opaque segment. `LocalVfs::resolve` (crates/cairn-backend-local/src/lib.rs:72-78) does `pb.push(seg.as_str())` per segment with no per-segment check; its doc comment ("VfsPath contains no `..` segments, so lexical traversal cannot escape the root") is false on Windows, where `PathBuf::push` of a drive-qualified string replaces the base and `\`-separated `..` is resolved by the OS at open time. `confined_real_path`/`local_path` (the canonicalize+starts_with check) is only used for the shell-out path, not for list/stat/read/write, which go through `resolve`. No `cfg(windows)` tests exist in cairn-types or cairn-backend-local.

Real ingress of untrusted strings: the AI executor (`crates/cairn/src/executor.rs:100-101 vpath`) parses LLM-supplied `path` strings and runs list/stat/read/copy/move against pane connections. LocalVfs instances rooted at something other than the drive root do exist: `$HOME` and saved-profile `path` LocalRoot connections (crates/cairn/src/connect/provider.rs:115-127, 165-177) and the remote-edit temp dir (app.rs:4457, 4844). The archive backend (security.rs:92-99) independently re-implements `\`→`/` normalization, UNC and drive-letter rejection, confirming the central type does not cover it.

Severity overstated as high. Mitigating facts: Windows-only (on Unix a backslash is a legal filename byte, so the segment is a literal file name and nothing escapes); the default panes are rooted at the drive root (app.rs:203-216 `split_cwd_root`), so lexical `..\` buys nothing there — only a `D:\...` segment reaches another drive; the AI path runs plan→confirm, so the user sees the raw path string before execution; plugin-returned paths (bridge.rs:358, 420) are consumed as data for the plugin's own VFS, not fed to LocalVfs. Net: a defense-in-depth guard that is documented as a trust-boundary invariant is silently false on one supported platform, with a concrete but user-confirmed vector. Medium.

**Fix:** Fix at the sink, not (only) the type: in `LocalVfs::resolve` reject any segment for which `std::path::Path::new(seg).components()` does not yield exactly one `Component::Normal` — on Windows that catches `\`-embedded `..`, drive prefixes (`C:`), and UNC in one platform-native check, while on Unix a backslash-bearing name stays a valid literal filename (it should; `\` is legal on ext4, SFTP, S3). Make `resolve` return `Result<PathBuf, VfsError>` (or fail closed to a NotFound/InvalidPath) and update its doc comment, which currently asserts an invariant that does not hold on Windows. Optionally add defense in depth in `VfsPath::parse`/`join`: reject a segment matching `^[A-Za-z]:` and a leading `\\` (UNC), which are never legitimate names on any backend; do NOT treat `\` as a separator in VfsPath — that would corrupt legitimate Unix/object-store keys containing backslashes. Let `cairn-backend-archive::validate_member_name` keep its `\`→`/` normalization (zip authoring convention) but drop its now-duplicated drive-letter check once the central one exists. Add `#[cfg(windows)]` tests in cairn-backend-local that `resolve`/`stat` of `..\..\x` and `D:\x` against a temp-dir root fail, and Unix tests that a file literally named `a\b` still resolves.

#### Object, Docker and K8s backends buffer whole files in RAM; PR #192 documents the lie instead of removing it

**~~high~~ → medium** · ❔ uncertain · correctness · effort L · lens `architecture` · also seen by bugs-container-backends, bugs-remote-backends  
`crates/cairn-backend-object/src/lib.rs`:96

(1) The buffering is pre-existing, and is already tracked as issue #189 (open) with a concrete plan and M5-4/M5-5 rows in IMPLEMENTATION_PLAN.md, gated on an RFC for resume-state format and on the `WriteHandle` Drop→abort net so aborted uploads don't leave billable orphaned parts. ## What the reviewers found genuinely good

- `architecture`: Reducer purity holds in the large: no I/O, no clocks, no runtime handles in cairn-core; a single non-test `unwrap()` mention in update.rs is inside a comment; render.rs is a pure function of `&AppState` with no state or I/O.

- `architecture`: Ports-and-adapters is applied consistently for the network backends (SftpOps/ContainerOps/KubeOps + in-memory mock + real adapter), so routing logic is unit-tested hermetically and live SDKs are quarantined behind features.
